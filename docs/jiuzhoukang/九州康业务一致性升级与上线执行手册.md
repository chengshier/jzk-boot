# 九州康业务一致性升级与上线执行手册

> 适用分支：`fix/jk-business-consistency`  
> 适用仓库：`jzk-boot`、`jzk-vue`、`jzk-app`  
> 数据库：MySQL 5.7  
> 本手册针对商品与库存统一、提现收款账户、发货拨货物流、异常收货、换绑阻断检查及后台页面可用性升级。

## 1. 上线结论与边界

本批代码已经完成静态检查和 CI 编译/构建，但尚未代替真实环境联调。生产上线必须遵守以下边界：

1. CRMEB 商品与 SKU 是唯一商品主数据，不再为九州康单独维护一套商品名称、规格和平台库存。
2. 普通零售与区县代平台订货共享 CRMEB 平台库存主账；九州康平台库存账户只保留业务冻结和流水镜像。
3. 提现申请只引用用户已维护的收款账户，由服务端生成不可变快照；前端不得自行拼接银行卡快照。
4. 异常收货 V1 只记录差异并阻断入库，不直接按实收数量部分入库，也不自动调整金额、佣金或索赔。
5. 异常处理完成后，原订货单或调拨单恢复到待收货状态，由收货人重新核对并执行正常全量收货。
6. 换绑审核使用实时阻断检查，历史订单归属不因换绑改变。

## 2. 上线前准备

### 2.1 代码版本冻结

确认三个仓库均使用同一批次的 `fix/jk-business-consistency` 最新提交，不允许只部署其中一个仓库：

- 后端：`jzk-boot`
- 管理端：`jzk-vue`
- 小程序/App：`jzk-app`

上线窗口开始后冻结九州康相关表结构、菜单、权限和业务状态的其他人工改动。

### 2.2 数据库备份

至少备份以下内容：

```sql
jk_withdraw_apply
jk_fund_account
jk_fund_flow
jk_platform_order
jk_platform_order_item
jk_stock_transfer
jk_stock_transfer_item
jk_stock_account
jk_stock_item
jk_stock_flow
jk_stock_batch
jk_agent_relation
jk_agent_relation_change_apply
jk_dict_type
jk_dict_item
eb_system_menu
eb_store_product
eb_store_product_attr_value
```

推荐进行一次完整数据库备份，并单独导出上述关键表。备份文件必须经过可读取验证，不能只确认命令执行成功。

### 2.3 配置敏感数据密钥

在系统配置中新增：

```text
配置键：jk_sensitive_data_secret
要求：至少 16 位，生产环境使用随机高强度字符串
```

要求：

- 不写入 Git 仓库、SQL 脚本或公开文档；
- 在密码管理系统或受控配置中心备份；
- 多实例后端必须使用同一个值；
- 密钥丢失或变更会导致历史银行卡快照无法解密；
- 首次配置后先在测试环境完成“添加银行卡—申请提现—后台查看—确认打款”全链路。

## 3. SQL 执行顺序

所有 SQL 均应在维护窗口执行。每一步完成后先检查脚本末尾的审计查询，再进入下一步。

### 第一步：提现收款账户

```text
sql/jiuzhoukang/fix/jk_withdraw_payee_account_upgrade.sql
```

作用：

- 创建独立收款账户表；
- 支持银行卡密文、摘要和掩码；
- 检查重复默认账户；
- 检查历史明文提现快照。

### 第二步：发货与拨货物流

```text
sql/jiuzhoukang/fix/jk_trade_logistics_upgrade.sql
```

作用：

- 为平台订货和库存调拨补充物流方式、物流公司、物流单号和实际发货/拨货时间；
- 检查已发货或已拨货但物流信息缺失的历史单据。

历史单据不得使用虚构物流公司或物流单号批量填充。自提或无需物流的单据必须使用明确的 `SELF_PICKUP` 语义。

### 第三步：异常收货

```text
sql/jiuzhoukang/fix/jk_trade_receive_exception_upgrade.sql
```

作用：

- 创建异常收货主表和商品差异明细表；
- 检查业务单状态与异常单状态是否一致；
- 检查实收、短缺和破损数量是否合法。

### 第四步：异常收货菜单与字典

```text
sql/jiuzhoukang/fix/jk_receive_exception_menu_status_upgrade.sql
```

作用：

- 增加 `RECEIVE_EXCEPTION`、`EXCEPTION` 等中文状态；
- 增加后台“异常收货处理”菜单；
- 增加列表和处理按钮 authority。

执行后需要在后台角色管理中给负责订货/调拨的运营角色授予：

```text
admin:jk:receive:exception:list
admin:jk:receive:exception:handle
```

权限分配完成后，相关管理员需要重新登录以刷新权限缓存。

### 第五步：只读一致性审计

```text
sql/jiuzhoukang/fix/jk_business_consistency_audit.sql
```

该脚本只用于发现问题，不应用任意一侧库存直接覆盖另一侧库存。出现差异时必须先追溯订单、冻结、出入库流水和批次形成过程，再制定修复 SQL。

## 4. 应用部署顺序

必须按以下顺序部署：

1. **数据库升级和配置项**；
2. **后端 `jzk-boot`**；
3. **后台管理端 `jzk-vue`**；
4. **小程序/App `jzk-app`**。

原因：管理端和 App 已开始调用新的汇总、库存详情、团队成员、推广素材、收款账户、物流和异常收货接口。前端先于后端部署会出现接口 404 或字段缺失。

后端部署后先验证：

```text
/api/admin/jk/receive-exception/list
/api/front/jk/receive-exception/list
/api/front/jk/withdraw/payee-account/list
```

未登录或无权限返回 401/403 属于正常安全行为；不能返回 404。

## 5. 必须执行的真实环境回归

### 5.1 普通零售共享库存

1. 普通用户正常浏览、加购、下单和支付；
2. 下单扣减 CRMEB 可售库存；
3. 取消未支付订单正确释放；
4. 退款/退货按原 CRMEB 链路恢复库存；
5. 同时创建区县代订货，确认两条链路不会超卖；
6. 九州康平台冻结镜像与 CRMEB 主账能够通过审计解释一致。

### 5.2 平台订货

1. 区县代创建订货；
2. 上传付款凭证；
3. 后台付款审核通过；
4. 库存不足时自动驳回且不残留冻结；
5. 物流配送必须填写公司和单号；
6. 自提无需填写物流单号；
7. 发货后正常收货入库；
8. 重复收货被拦截；
9. 发货前关闭正确释放冻结；
10. 异常收货上报后不入库、不触发完成业绩。

### 5.3 库存调拨

1. 创客或合伙人申请调拨；
2. 所属区县代审核；
3. 上传付款凭证并确认付款；
4. 拨货时填写物流或选择自提；
5. 正常收货后下级库存入账；
6. 异常收货上报后区县代库存不重复出库、下级库存不入账；
7. 平台处理完成后恢复待收货，再次正常收货只入账一次；
8. 关闭、驳回和取消路径正确释放冻结。

### 5.4 异常收货

至少验证四种情况：

- 数量短缺；
- 商品破损；
- 短缺并破损；
- 无数量差异但存在包装、物流等其他异常。

检查：

1. 每种商品必须提交完整核对明细；
2. 实收不能大于应收；
3. 破损不能大于实收；
4. 同一业务单不能存在两条待处理异常；
5. 同一 `requestNo` 重试返回原异常记录，不重复创建；
6. 处理中不能正常收货；
7. 处理完成或驳回后恢复原待收货状态；
8. 异常处理本身不产生库存和佣金流水。

### 5.5 提现

1. 添加、编辑、删除和设为默认银行卡；
2. 同一用户重复银行卡被拦截；
3. App 只显示掩码；
4. 提现申请只提交 `payeeAccountId`；
5. 修改银行卡不改变历史提现快照；
6. 无确认打款权限的管理员不能查看完整卡号；
7. 有权限管理员主动查看时可解密；
8. 审核驳回释放冻结金额；
9. 重复确认打款被状态机或幂等机制拦截。

### 5.6 换绑

对每一个结构化阻断项分别制造测试数据：

- 当前关系已变化；
- 目标上级无有效身份或被冻结；
- 跨区域；
- 存在未完成调拨；
- 存在可用或冻结库存；
- 存在待结算佣金；
- 存在处理中提现。

确认后台详情能展示具体当前值、阻断原因和处理建议，且存在阻断时不能审核通过。

## 6. 监控与上线后观察

上线后至少观察一个完整业务日：

- `jk_business_event` 是否存在持续失败事件；
- 库存冻结、释放、出库和入库是否成对；
- `RECEIVE_EXCEPTION` 是否存在没有对应异常单的孤立业务；
- 异常单已处理但业务单仍停留在异常状态；
- 提现申请存在空收款快照或无法解密；
- 发货/拨货状态与物流字段不一致；
- 普通零售和平台订货并发时是否出现负库存或超卖。

发现金额、库存或权限越权问题时，应立即停止相关业务入口，而不是只修改前端展示。

## 7. 回滚原则

### 7.1 可以直接回滚的内容

- Admin 和 App 静态资源；
- 未产生新业务数据前的后端版本；
- 新增菜单的显示状态。

### 7.2 不能简单回滚的内容

一旦产生以下新数据，不允许只回滚代码而保留不兼容数据：

- `jk_withdraw_payee_account` 加密银行卡；
- 新格式提现快照；
- 平台订货/调拨物流字段；
- `jk_trade_receive_exception` 异常单；
- 原业务单 `RECEIVE_EXCEPTION` 状态。

需要回滚时，应先停止写入，导出新增数据，核对每一条业务单和账户状态，再执行人工回退方案。禁止删除异常单后直接把所有订单批量改为已收货或已入库。
